# 2. Product Definition

OpenContract is a public procurement transparency and verification platform.

Its purpose is to make procurement information easier to understand, trace, verify and audit by creating a structured public record of procurement events and cryptographic proofs.

OpenContract is an **accountability and verification layer**.

It is NOT:

* a replacement for an official government procurement platform;
* a replacement for GHANEPS;
* a court;
* an anti-corruption enforcement authority;
* a financial institution;
* a procurement regulator;
* an automated legal decision-maker;
* proof that a procurement process was honest;
* proof that information submitted by an authorized user is factually true;
* a system that stores sensitive bidding information publicly on-chain.

The platform records and verifies information that has been entered into the system.

Blockchain provides tamper-evident anchoring of selected records and hashes. It does not magically establish the truth of the underlying information.

The system should follow this conceptual architecture:

```text
                    ┌────────────────────┐
                    │   Public Web App   │
                    └─────────┬──────────┘
                              │
                    ┌─────────▼──────────┐
                    │ Application / API  │
                    └─────────┬──────────┘
                              │
          ┌───────────────────┼───────────────────┐
          │                   │                   │
 ┌────────▼────────┐ ┌────────▼────────┐ ┌────────▼────────┐
 │   PostgreSQL    │ │ Document Store  │ │ Blockchain      │
 │   Source Data   │ │ Files + Hashes  │ │ Proof / Anchors │
 └─────────────────┘ └─────────────────┘ └─────────────────┘
                              │
                    ┌─────────▼──────────┐
                    │ Intelligence Layer│
                    │ Signals + AI       │
                    └────────────────────┘
```

PostgreSQL is the application's primary structured data store.

Blockchain is an integrity/proof layer.

Object storage contains documents.

The AI layer consumes structured application data through controlled server-side functions.

# 7. Source of Truth Rules

The following rules are mandatory.

## 7.1 Database

The PostgreSQL database is the application's canonical structured data source.

## 7.2 Blockchain

Blockchain stores cryptographic proofs and event anchors.

The blockchain is NOT the primary relational database.

## 7.3 Documents

Documents are stored off-chain.

Their cryptographic hashes can be anchored on-chain.

## 7.4 AI

AI must never become the source of truth.

AI responses must be generated from application data and clearly identify the records supporting the answer.

## 7.5 UI

The frontend must never invent data.

All displayed procurement information must come from:

* the database;
* approved deterministic calculations;
* blockchain verification;
* or explicitly marked demo data.

# 23. Document Verification

Document verification is a core product feature.

The process:

```text
User uploads document
        ↓
Read exact bytes
        ↓
Calculate SHA-256
        ↓
Search registered document hashes
        ↓
Compare
        ↓
Display verification result
```

Possible outcomes:

### VERIFIED

The uploaded file's SHA-256 hash matches a registered document hash.

### MISMATCH

The uploaded file does not match the registered hash.

### NOT REGISTERED

No matching document hash exists.

### PENDING

A registered document exists but blockchain anchoring is still processing.

### ERROR

The verification process could not complete.

The UI must explain these states clearly.

---

# 24. Important Hashing Rule

Hash the exact uploaded bytes.

Do NOT hash:

* the filename;
* a database ID;
* extracted text;
* a URL;
* a generated JSON representation;

unless that is explicitly a separate documented hashing operation.

For document verification, SHA-256 should be calculated over the exact file bytes.

# 30. Blockchain Processing

Blockchain transactions should preferably be asynchronous.

Recommended flow:

```text
Database transaction
       ↓
Outbox record
       ↓
Blockchain worker
       ↓
Transaction submitted
       ↓
Transaction confirmed
       ↓
Database anchor updated
```

A blockchain RPC failure must not corrupt the procurement database transaction.

Retries must be idempotent.

# 31. Integrity Signals

The platform may generate deterministic review signals.

Examples:

### Single bidder

A tender received only one recorded bid.

### Significant amendment

Contract value increased beyond a configured threshold.

### Delayed implementation

Recorded milestone dates indicate significant delay.

### Missing update

An expected procurement stage has no corresponding public record.

### Supplier concentration

A supplier appears across an unusually high number of procurement records within the available dataset.

These are signals for review.

They are NOT findings of wrongdoing.

---

# 32. Signal Language

Allowed:

> Review signal

> Requires additional review

> Contract value increased by 24%.

> Only one bid was recorded.

Not allowed:

> Corruption detected.

> Fraud detected.

> This official is corrupt.

> This contractor committed fraud.

> This procurement is illegal.

unless an explicitly authorized future workflow establishes such a determination from a competent authority.

---

# 33. Signal Severity

Use:

```text
INFO
LOW
MEDIUM
HIGH
```

Severity is a product classification for review priority.

It is not a probability of corruption.

Do not represent severity as certainty.

---

# 34. Integrity Signal Explainability

Every signal must explain:

1. What triggered it.
2. Which procurement record was inspected.
3. Which values were compared.
4. The calculation used.
5. Why the signal was created.
6. What the user should review.

Example:

```text
Review signal

Contract value increased by 24%.

Original value:
GHS 1,000,000

Amended value:
GHS 1,240,000

Change:
+GHS 240,000 (+24%)

Reason recorded:
Additional works

This signal does not establish wrongdoing.
```

# 68. Definition of Done

A feature is NOT complete merely because its UI exists.

A feature is complete only when:

* UI exists;
* backend exists;
* validation exists;
* authorization exists;
* database interaction works;
* error handling works;
* loading state exists;
* empty state exists where applicable;
* success state exists;
* mobile behavior works;
* accessibility has been considered;
* tests exist where appropriate;
* no fake functionality is being represented as real.
